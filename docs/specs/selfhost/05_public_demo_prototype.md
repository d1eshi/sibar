# Self-Hosted Public Demo Prototype

## Goal

Turn the self-hosted execution layer into a public, visual demo that explains
the product idea without asking people to read specs, JSON reports, or eval
output.

This spec does not replace `01-04`. It packages their loop into a simple,
shareable prototype that lets external users understand the promise and give
feedback before the full execution layer or SwiftUI surface is complete.

Public objective:

```text
SIBI helps you understand what you built: it asks before explaining, detects
gaps, shows evidence, proposes repair, and declares bounded readiness.
```

## Source Specs

The demo must preserve these contracts:

1. `01_selfhost_boundary.md`: show the bounded artifact slice being studied.
2. `02_evaluation_contract.md`: show how a freeform answer becomes a readiness
   finding or a typed gap.
3. `03_product_improvement_loop.md`: show repair, retry, and readiness
   limitation after a gap.
4. `04_selfhost_gap_detection_benchmark.md`: show that the demo represents
   evaluated behavior rather than generic chat output.

It also draws narrative and visual direction from:

1. `docs/product/01_moat.md`: SIBI is codebase learning infrastructure, not a
   repo chat wrapper.
2. `docs/product/02_v01_scope.md`: the public demo should follow the golden
   path and minimum useful demo.
3. `docs/specs/10_study_panel_ui.md`: the eventual product surface can be a
   native study panel, but this public demo is web-first and fixture-based.

## Feature Outcome

The public user receives a short, shareable demo that makes the Build-to-Learn
loop legible:

```text
landing
  -> interactive demo
  -> artifact slice
  -> attempt-first question
  -> user answer
  -> gap or readiness finding
  -> evidence
  -> repair
  -> retry
  -> bounded readiness
  -> feedback prompt
```

The demo should make one idea obvious:

```text
SIBI does not just explain code. It checks whether you can own a bounded part of
the system and tells you what to repair before you touch it.
```

## Public Demo Shape

The first public demo is a simple web experience that can be deployed to
Vercel, Netlify, or GitHub Pages.

It uses fixture data only. It does not require a backend, live repo ingestion,
account creation, model calls, or SwiftUI.

The demo has three areas:

1. **Narrative**
   Explain what SIBI is, who it is for, and why it is different from generic
   code chat.
2. **Demo**
   Walk through one simulated self-hosted codebase slice with five answer
   states:
   - grounded
   - uncited
   - partial
   - overconfident wrong
   - design-induced confusion
3. **Feedback**
   Ask the reviewer what they understood, what confused them, whether they would
   use this for AI-generated software, and what they would want to try with
   their own codebase.

## Demo Content Contract

The demo must include:

1. an artifact boundary label and included/excluded scope
2. a short artifact slice preview
3. one attempt-first ownership question
4. a way to select or enter a user answer
5. an observed finding: readiness or typed gap
6. user evidence and repo evidence shown side by side
7. a repair prompt when the answer is insufficient
8. a retry or re-evaluation step
9. a bounded readiness statement
10. a feedback prompt

The demo must not claim:

1. that SIBI can analyze any repo yet
2. that SIBI understands the whole codebase from one answer
3. that a single correct answer means durable ownership
4. that the public demo is the full product

## Manual Harness

Review the public demo with two or three people who have not read the specs.
Each reviewer should answer:

1. What problem does SIBI solve?
2. Why is this different from asking a chat model to explain code?
3. What does `readiness` mean in the demo?
4. Which part of the flow was confusing?
5. Would you want to try this on software generated by an agent?
6. What would you need before trusting the readiness judgment?

A reviewer passes the comprehension test when they can explain:

```text
SIBI asks me to reason first, compares my answer to evidence, gives a repair
when I miss something, and only makes bounded readiness claims.
```

## Eval Coverage

The public demo is not itself the source of truth. It should be backed by:

1. the self-hosted manifest and mastery checks
2. the freeform evaluator slice
3. the self-hosted benchmark report
4. regression tests for gap/readiness outputs used in the demo fixtures

The demo may use fixture outputs from the current first-slice evaluator, but it
must label them as demo data.

Missing coverage before wider public release:

1. full 40-case freeform evaluator coverage
2. generic chat baseline comparison
3. repair and re-evaluation execution beyond fixture presentation
4. feedback synthesis from external reviewers

## Acceptance Gate

The public demo is ready to share when:

1. a reviewer understands the loop without reading specs
2. the demo does not promise arbitrary repo analysis
3. boundary, attempt-first, evidence, repair, retry, and readiness are visible
4. feedback can be collected from external reviewers
5. the demo can be deployed to Vercel, Netlify, or GitHub Pages
6. the demo uses fixture data and clearly labels itself as a prototype
7. the demo does not contradict the moat or v0.1 scope
