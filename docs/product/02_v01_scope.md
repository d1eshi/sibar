# v0.1 Scope

## Release Goal

v0.1 proves one end-to-end Build-to-Learn session.

It does not need to be broad. It needs to be reproducible.

## Golden Path

```text
1. User selects or imports one real artifact.
2. Sibi creates a small artifact map.
3. Sibi creates a concept map from that artifact.
4. Sibi runs a guided autopsy.
5. User answers ownership questions.
6. Sibi detects gaps and misconceptions.
7. Sibi assigns one or more practice challenges.
8. Sibi stores evidence and emits a readiness report.
```

## Artifact Types

v0.1 should support one of these first:

1. a small repo generated by an agent
2. a bounded folder in a larger repo
3. a handpicked set of files from `agent-evaluator` or Sibi itself

The best dogfood path is a real artifact built with agents, because that matches the moat.

## Success Metrics

A v0.1 session succeeds if the user can show evidence for at least three outcomes:

1. explain: describe what the artifact does and why the main parts exist
2. trace: walk through one important flow across files
3. modify: make or specify one safe bounded change
4. debug: predict one likely failure mode
5. recall: reconstruct the flow after 24 hours
6. transfer: apply the concept to a second small artifact

## Hard Cuts

These are out of v0.1 unless they directly support the golden path:

1. macOS observer process detection
2. ambient capture
3. voice
4. OCR or screen spotlight
5. Vim/Neovim bridge
6. browser scraping
7. workspace/API sync
8. team onboarding dashboards
9. full AI project generation

## Minimum Useful Demo

The demo should not show Sibi explaining a file.

The demo should show:

```text
artifact -> prediction -> wrong/incomplete answer -> detected misconception -> hint -> retry -> updated understanding memory -> readiness report
```

The important line is:

> You are ready to make this change.

## Article Reader Persistence Note

The article reader demo should keep login out of the first validation loop.

For the public MVP, session-only notes are enough to validate the learning
gesture: paste a source, read, highlight evidence, write atomic notes, and see
whether the user understands the source better.

`localStorage` is an acceptable technical bridge after the gesture is validated.
It can preserve article notes on the same browser without forcing account
creation. That should still be treated as local device persistence, not product
memory.

Durable persistence should wait until there is a user profile. At that point,
each note should be associated with:

1. user profile id
2. article canonical URL
3. article title and host
4. selected evidence text and paragraph index when available
5. note kind: highlight, question, or idea
6. note text and creation time

Do not add login just to save notes. Add login when users explicitly need to
recover notes across devices, build a learning history, or connect article notes
to the broader understanding memory.
